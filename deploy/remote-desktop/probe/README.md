# ArkWeb read-only media probe

This developer fixture tests browser screen capture → WebRTC → a real HarmonyOS
App's bundled ArkWeb page. It does not inject OS input or use account/Agent state.
The temporary signaling server binds only `127.0.0.1:18765`; `hdc rport` carries
signaling, while WebRTC media uses the real device network and optional trial TURN.
USB signaling is not evidence of production Relay authentication or public HTTPS.

## Run

1. Deploy the isolated authenticated coturn described in the parent runbook.
   Verify an unauthenticated Allocate returns 401 before opening the test.
   Keep its secret outside Git. Use **distinct** short-lived REST usernames for
   sender/receiver, one TURN URL per test, and bounded allocation/traffic budgets.
2. Create a private local JSON file (mode 0600) with this shape. The arrays contain
   ordinary RTCIceServer objects with `urls`, `username`, `credential`:

   ```json
   {
     "accessKey": "fresh-random-local-probe-key",
     "iceServers": [],
     "receiverIceServers": [],
     "evidenceFile": "/private/local/path/events.ndjson"
   }
   ```

   Fill both arrays with valid trial credentials. Never commit the real file.
   Credentials only grant TURN resources, not product/OS control.
3. Start `RD_PROBE_CONFIG=/private/local/path/config.json node server.mjs` from
   this directory. Open `http://127.0.0.1:18765` in desktop Chrome. API access uses
   the local HttpOnly SameSite cookie; native requests use the generated key.
4. Build the HarmonyOS debug HAP using its nearest AGENTS guide and install as an
   update. The receiver JS is generated by `entry/hvigorfile.ts`; edit this
   directory's `receiver.js`, not the generated rawfile copy. Match the device's
   installed version for local packaging if necessary; do not uninstall/reset data.
5. Run `hdc rport tcp:18765 tcp:18765`, then explicitly launch the debug fixture. Set `PROBE_BUNDLE_ID` to the published
   `bundleName` in the HarmonyOS `AppScope/app.json5`; keep that upgrade identity:

   ```text
   hdc shell aa start -a EntryAbility -b "$PROBE_BUNDLE_ID"
       --ps openbitfunRemoteDesktopProbe true
       --ps remoteDesktopProbeKey <local-probe-key>
   ```

   Add `--ps remoteDesktopProbeLandscape true` for a wide landscape window.
   The launch path is gated by BuildProfile.DEBUG. It does not navigate the normal
   App or expose account credentials to JS. No camera/microphone is needed.
6. Choose normal ICE or forced TURN VP8/H264, then choose the **probe tab** in the
   browser's capture picker. Each capture is limited to 60 seconds and 350 kbps;
   inspect the saved selected candidate types, decoded/presented frame progress
   and echo RTT. `connected` or a relay candidate alone is insufficient.
7. Capture native compact/wide screenshots, background the App and check cleanup,
   then start a new run to verify return. Normal ICE may select relay; never call
   that P2P success. Browser capture, synthetic frames and native display sources
   are different evidence scopes. Physical folding requires a separate real test.
8. Stop capture, return to ordinary EntryAbility without probe parameters, remove
   the dedicated hdc reverse rule (`hdc fport rm tcp:18765 tcp:18765`,
   without quoting both node arguments together), stop the loopback server and idle trial TURN.
   Keep only sanitized evidence in a local ignored `.openbitfun/` directory.

## Native sender

Stage 1 uses the [macOS native display probe](../../../src/apps/desktop/probes/remote-desktop/README.md)
in place of desktop Chrome. It reuses this bounded signaling/ArkWeb fixture,
requires an explicit display and local OS consent, and publishes a fresh run.
Answer reads and writes both bind to runId; old answers cannot bind to a newer sender.
Browser capture evidence and native display evidence must remain separate.

## Trial constraints

The production macOS sender can also exercise the **product shared receiver**
instead of this legacy echo page. Update an isolated DEBUG HAP without changing
its installed identity/data, then run from the repository root:

```sh
OPENBITFUN_RD_NATIVE_MEDIA_CONFIG=/private/local/native-media-config.json \
  node scripts/test-remote-desktop-harmony-media.mjs --display macos:<uuid>
```

The optional private configuration has `force_relay: true`, `ice_servers` and
`receiver_ice_servers`; the two roles use distinct short-lived RTCIceServer
credentials and one URL/transport each. It contains no TURN signing secret.
The runner owns loopback port 18765 and the DEBUG launch/reverse rule for its
bounded run; stop the legacy probe server first. It checks actual native source,
shared-page presentation, selected pairs, both endpoints' `relayProtocol`,
source-only stop expiry and drainage, then restores the ordinary trial App.
Its file/USB signaling is not account authentication, public HTTPS or cellular
evidence. Do not treat the small dynamic test's bitrate as a desktop quality
benchmark. Idle trial TURN after the session and verify allocations are released.

Use `bundlePolicy=max-bundle` and one TURN transport at a time. A low per-user quota
shared by both endpoints can reject the receiver with 486. Allocation release may
lag PC close; cap its lifetime and verify renewal/expiry rather than treating close
as guaranteed immediate deallocation.

The coturn image runs unprivileged. A root-owned mode-0600 config is unreadable to
it, and turnserver can then start without the intended auth settings. Match the
mounted file owner to the container UID; test config readability and anonymous
rejection. The pinned image used for the initial trial was coturn 4.6.3, digest
`sha256:71c3c990283385567f11794ee692e3a47b66fd9b0bb39e42afbe776e331dd888`.

For two relay candidates on the same NATed host, coturn may map its advertised
public address back to its private relay address. Allow that **single relay
address** only when a dedicated process-UID firewall rule also prevents access to
its other UDP ports. The parent runbook owns this trial-specific rule and rollback.
Do not broadly remove the private/management-network deny rules.

Node syntax, Harmony architecture, HAP compilation, and theme audits cover source
quality. Actual ArkWeb decoding/presentation, candidate pair and DataChannel echo
must come from the real device. A valid server-side STUN response is only port
reachability, not successful TURN allocation or media transfer.
